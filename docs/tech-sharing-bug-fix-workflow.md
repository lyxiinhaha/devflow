# DevFlow Bug 修复全流程：从混乱到可控

> 技术分享 | DevFlow 工程实践系列

---

## 引言：我们为什么需要一套流程？

在日常开发中，Bug 修复往往是最"随缘"的一环。

典型的混乱场景：
- 收到 issue，直接打开代码开改，改完提交，然后发现没复现；
- 不知道改哪里，grep 全库，碰运气；
- 改完发现影响了其他模块，紧急回滚；
- 验证方式全靠人工拍脑袋，没有清单，没有记录；
- 同样的 Bug 隔几个月又出现，因为没有复盘，没有沉淀。

**这不是工程师的问题，而是流程缺失的问题。**

DevFlow 的 `fix` 工作流试图把"修 Bug"这件事从一门玄学，变成一套可重复、可审计、有质量门禁的标准作业。

---

## 全流程总览

```
输入 (Meegle URL / ID / 描述)
    │
    ▼
Step 0  输入门禁 + 工作项创建
    │
    ▼
Step 1  读取 Issue + 信息完整性校验
    │
    ▼
Step 2  根因分析（四阶段 CodeGraph 法）
         ├─ 定位入口符号
         ├─ 爆炸半径评估
         ├─ 确认最小代码点
         └─ 评分门禁（≥90 才能进入修复）
    │
    ▼
Step 3  执行修复（最小改动原则）
    │
    ▼
Step 4  生成 Bug 修复清单
    │
    ▼
Step 5  输出摘要，等待人工验证（不自动提交）
    │
    ▼
Step 6  收到验证通过信号 → 提交
    │
    ▼
Step 7  更新 Meegle 状态 + 强制触发复盘
```

每一步都有明确的输入、输出和门禁条件，任何一步失败都有对应的失败处理路径，不会静默跳过。

## 每个阶段的设计思路与好处

### Step 0：输入门禁与工作项创建

**做什么：** 解析输入（URL 或 ID），创建本地工作项目录，支持批量视图自动枚举。

**为什么重要：**

传统做法是"给我一个 issue 链接，我去看"——这有两个隐患：

1. **批量视图被当成单条处理**：把一个包含 20 个 bug 的看板 URL 丢过来，AI 只看了第一条。DevFlow 会识别 URL 类型（`workitem_detail` vs `view`），批量时自动翻页枚举所有条目，建立队列。

2. **没有结构化存储**：修复过程全在对话里，一关窗口什么都没了。工作项目录 `.devflow/work-items/` 在本地落地，`meta.json` 记录状态机，`sanitized.md` 存储清理后的 issue 内容供后续步骤消费。

**好处：**
- 批量 bug 一条指令全处理，不用逐一手动
- 过程可追溯，工作状态持久化
- raw/sanitized 分离，防止 Meegle 原始内容中的 prompt 注入风险

---

### Step 1：信息完整性校验

**做什么：** 读取 issue 全字段 + 评论 + 附件，校验必须项。

**必须项（缺一则失败）：**
- 仓库地址与分支名称
- Bug 现象描述  
- 预期行为描述

**为什么重要：**

"必现"和"偶现"是不同问题；"在 A 页面闪退"和"在 A 页面点击 B 按钮后偶现闪退"是不同的调试目标。在信息不完整时动手，往往只是在猜测，而不是在修复。

**好处：**
- 强制在分析前获取足够上下文，避免方向性错误
- 仓库/分支来源有优先级策略，当前工作区匹配时强制复用，不做无意义的 worktree 创建

---

### Step 2：四阶段 CodeGraph 根因分析

这是整个流程的核心，也是与传统 "grep + 凭经验" 差异最大的地方。

#### 阶段一：定位入口符号

```bash
devflow-cg explore "条件单列表触发条件文案生成"
```

查询可以是自然语言，也可以是符号名。CodeGraph 返回相关符号的**逐行源码 + 调用路径**，等效于已经 Read 了那些文件，可以直接据此 Edit，不用再重复打开文件。

**传统做法的代价：**
- `grep -rn "conditionText" .` 可能返回 200 个结果
- 逐个 Read 过滤，消耗大量 token 和时间
- 动态分发（接口/抽象类）grep 根本找不到

**CodeGraph 的优势：**
- 一次查询返回相关符号，已解析动态分发路径
- 每次 CG 查询约等效节省 10 次 grep/read
- 累计调用节省数据写入 `workspace.json`，可量化效率收益

#### 阶段二：爆炸半径评估（最重要的门禁）

```bash
devflow-cg explore "<根因方法名> 调用方 影响"
```

| 直接调用方数量 | 风险等级 | 行为 |
|---|---|---|
| 0–2 | LOW | 继续 |
| 3–10 | MEDIUM | 列出受影响模块，继续 |
| 11–30 | HIGH | **暂停，等用户确认** |
| 30+ | CRITICAL | **强制拦截**，要求专项重构方案 |

**为什么这个门禁很关键：**

改一个"看起来很小"的方法，可能影响几十个调用方，引发大范围回归。这种情况下应该提交 RFC，而不是悄悄改掉。爆炸半径门禁让 AI 不能"自作聪明"地做高风险改动，必须拉人确认。

#### 阶段三：确认最小代码点

精确到 `文件路径:行号`，摘录修改前后各 2-3 行上下文，量化偏差（预期行为 vs 实际行为）。

#### 阶段四：原子修复方案 + 修复后影响面验证

**关键设计：修复后必须再做一次影响面检查。**

```bash
devflow-cg explore "<修改后符号> 影响"
```

强制断言：**影响面不得扩大**。如果一个"修复"导致更多模块受影响，说明方案有问题，必须调整后重新验证。

---

### 评分门禁：90 分才能动代码

对每个 Bug 的分析质量打分（0–100）：

| 维度 | 权重 |
|---|---|
| 信息完整性（仓库/分支/现象/预期） | 20 分 |
| 根因定位质量（有代码证据） | 30 分 |
| 修复方案质量（最小、安全、可执行） | 25 分 |
| 影响范围与风险说明 | 15 分 |
| 验证方案可执行性 | 10 分 |

**只有总分 ≥ 90（A 级）才进入修复模式。**

低于 90 分时会明确告知缺失了什么，要求补充，而不是"差不多就改吧"。

**这个门禁解决的核心问题：**
- 分析质量低时不修复，避免"改错了"的情况
- 评分维度透明，修复质量可量化
- 对 AI 自己的分析结果做约束，防止过度自信

---

### Step 3：最小修复原则

**三条铁律：**
1. 只修当前 bug 所需内容
2. 不引入新抽象、新依赖
3. 修复完成后**不自动提交**

**为什么不自动提交？**

这是流程里最反直觉的设计，也是最重要的设计。

AI 可以写代码，但 AI 不应该是代码的最终责任人。每一次提交都应该有人类的眼睛过一遍 `git diff`。自动提交是在用便利性换走工程师对代码的所有权。

**批量隔离规则：** 多条 bug 顺序修复时，每条开始前确认上一条已暂存且 `git status` 为 clean，防止不同 bug 的改动混在同一个 commit 里。

---

### Step 4：Bug 修复清单

每个 bug 生成独立的清单文件：

```
.bugfix-records/260806/7063916058-条件单触发文案未跟随多语言-bug修复清单.md
```

清单包含：基本信息、Bug 描述、影响范围、根因分析（含代码证据）、解决方案、验证方法、提交信息模板。

**这份清单的价值不只是当下：**

- 3 个月后同一个 bug 复现，历史清单是最好的上下文
- Code Review 时审查者可以对照清单检查改动是否符合预期
- 团队 onboarding 时，这些清单是真实的案例库
- 复盘时，清单是经验沉淀的原材料

---

### Step 5：人工验证门禁

所有修复完成后，流程**停下来等人**：

```
✅ 本轮修复已完成，等待人工验证后逐条提交。

确认每条验证通过后，请告知「第 N 条验证通过」或「全部验证通过」
```

这是流程里的第二个人工介入点（第一个是爆炸半径 HIGH 时）。

**验证建议自动生成：** 根据 bug 描述和修复方案，给出具体的人工验收步骤和回归场景，不是让开发者自己想"我该测什么"。

---

### Step 7：强制复盘

提交完成后，流程**不允许就这样结束**。

1. 自动更新 Meegle 状态，添加修复完成评论（含根因摘要、修改文件、评分）
2. 触发经验卡草稿生成，提示执行 `devflow retrospect` 入库

**为什么要强制？**

复盘是可选项时，99% 的情况下不会做。一旦变成强制，才会真正形成团队的经验积累。经验卡记录的是"为什么这样改，有哪些坑"，而不仅仅是"改了什么"——这是 git log 无法替代的内容。

---

### Step 3.5：重排查模式

当 bug 被重开（验证不通过）时，流程不是简单地重走一遍，而是：

1. 读取上次修复清单，提取历史根因和失败现象
2. 重新追踪调用链，重点关注边界值/时序/竞态等遗漏路径
3. 添加结构化调试日志（`[BUGFIX_<issue_id>]` 前缀）
4. 等待开发者提供日志后再做实际修复

**关键约束：提交前必须清除所有临时日志。**

```bash
grep -rn "BUGFIX_<issue_id>" <仓库目录>
```

有残留则拒绝提交。调试日志污染生产代码是一个常见但容易被忽视的问题，这里用工具强制保证。

## 与传统方式的对比

| 维度 | 传统方式 | DevFlow fix 流程 |
|---|---|---|
| 信息收集 | 手动看 issue，可能遗漏 | 结构化读取，完整性校验 |
| 代码定位 | grep 碰运气 | CodeGraph 符号级精准定位 |
| 影响评估 | 凭经验估 | 自动爆炸半径计算 + 风险分级 |
| 修复质量 | 没有标准 | 90 分评分门禁 |
| 提交时机 | 改完就提 | 人工验证后才提交 |
| 过程记录 | 全在对话里 | 标准化清单文件，持久化存储 |
| 经验积累 | 凭记忆 | 强制复盘，经验卡入库 |
| 批量 bug | 逐一手动 | 自动枚举队列，顺序隔离处理 |

## 几个值得单独讨论的设计决策

### 1. 为什么是 90 分而不是 80 分？

80 分允许较多"模糊通过"的分析，90 分意味着每个维度都不能有明显短板。Bug 修复的成本不只是写代码的时间，还包括回归测试、验证、发版。一个分析质量低的修复引发的二次 bug，代价远大于等待信息完整再修的成本。

### 2. 为什么不合并批量 bug 的 commit？

每个 bug 对应一个独立 commit，便于 `git bisect`、cherry-pick 和 revert。合并成一个 commit 看起来整洁，实际上是在牺牲可操作性换取表面整洁。

### 3. CodeGraph 不可用时怎么办？

流程有明确降级路径：使用 grep/find + Read 手动搜索，在分析文件中注明"CodeGraph 不可用，使用手动搜索"。效率会下降，但流程本身不中断。这是"优雅降级"而非"硬依赖"。

### 4. 为什么要 sanitized.md 和 raw.md 分开？

`raw.md` 存原始 Meegle 内容，AI 后续只读 `sanitized.md`。这是防止 prompt 注入的防御措施——外部系统的内容不应该直接作为 AI 的指令源。在安全意识还不普遍的工程实践中，这种分离值得养成习惯。

## 真实案例

以下两个案例来自同一个项目，时间相差一天，一个被门禁拦截，一个 100 分通过——正好形成对照。

---

### 案例 A（失败）：止盈止损改单页气泡定格 `--`

**Issue #7067404642 | 2026-08-06 | 评分 70/100 → 拒绝修复**

**Bug 描述：** 止盈止损单改单页，不对上涨/下跌触发价做修改，只是把光标放过去，气泡里的触发价和止损金额就会显示 `--`，而不是原本已有的值。

**分析过程（节选）：**

流程完整走完了 CodeGraph 四阶段，数据流追踪到以下层次：

```
气泡文案来源
  └─ state.bracketProfitLossHint?.riseText / fallText
       └─ ProfitLossHintResolver.resolve()
            └─ trigger.takeProfitRefTriggerPrice（由算价写入）
                 └─ ConditionalPlaceOrderPresenter.launchCalcEntrustPriceDebounced()
```

同时定位了两个叠加断点：

1. **Focus 断点**：改单页的触发价百分比字段 focus 时，不派发任何算价 Action（对比止盈价/止损价字段的 focus 会派发 `FocusTakeProfitPrice / FocusStopLossPrice`）。

2. **初始化静默失败**：`launchCalcEntrustPriceDebounced` 在三种情况下会静默 return 而不写回：holding 为空、basicPrice+currentPrice 都为空、接口返回失败。

**为什么 70 分，拒绝修复：**

| 维度 | 得分 | 原因 |
|---|---|---|
| 信息完整性 | 12/20 | 无复现步骤、日志、录屏 |
| 根因定位质量 | 20/30 | 数据流完整，但三条静默失败路径未从候选中锁定一条 |
| 修复方案质量 | 20/25 | focus 补发方向可行，但未覆盖三条路径，盲目落地可能无效 |
| 影响范围与风险 | 12/15 | 委托价保护边界需人工核对 |
| 验证方案 | 6/10 | 缺稳定复现序列 |
| **总分** | **70/100** | **F 级，拒绝** |

这里有一个反直觉的地方：**分析内容其实相当深入**——调用链、断点位置、三条候选路径全都找到了，失败分析文件写了将近 100 行。但 90 分门禁关心的不是"分析了多少"，而是"能否对根因做出确定性断言"。

三条候选路径中任何一条命中都会产生完全一样的症状，在没有 logcat 的情况下，盲目落地 focus 补发方案：
- 若命中路径 1（holding 为空），补发也不会进入算价，修复无效
- 若命中路径 2（basicPrice 为空），同样 return，无效
- 若命中路径 3（接口失败），补发有效但可能引入高频无效请求新问题

**流程的输出不是"无法修复"，而是"还差一步"：**

```
根据日志将 70/100 提升到 90/100 后再进入修复：

若 asyncWriteback bracket 未输出
  → 命中 holding 缺失或 basicPrice 空
  → 修复方向：用 currentPrice 兜底 + focus 补发

若 basicPrice 有值但 takeProfitRef 为空
  → 命中接口失败
  → 修复方向：focus 补发 + 接口错误上报

若 asyncWriteback 有输出且值正确，但气泡仍 --
  → 渲染层 pendingBubbleModel 更新时序问题
  → 修复方向转到 TriggerPriceUpComponentView.render
```

这是这个案例最值得关注的地方：门禁拦截之后，流程给出的不是一个"错误"，而是一份精准的"排查指引"——下一步应该拿什么日志、看什么字段、每条路径对应什么修复方向。这比"改了再看"省的时间多得多。

---

### 案例 B（成功）：账户页条件单成交回报后只刷新数量接口

**Issue #7068108607 | 2026-08-07 | 评分 100/100 → 单行修复**

**Bug 描述：** 账户页条件单 Tab，收到成交回报后，只有数量角标接口（`queryCountData`）被调用，未完成/已完成列表不刷新，需手动下拉才能更新。

**症状与根因的距离：**

从症状看，这像是"成交回报没有触发列表刷新"，直觉上会去找成交回报的订阅逻辑，给它加一个列表刷新调用。但这样改是错的——职责混乱，而且没有找到真正的断点。

四阶段分析追踪了完整调用链：

```
StockDeliverSubscription.stockDeliverFlow（成交回报）
    │
    ├─ SecondTabPresenter.init 监听
    │    └─ refreshCounts() → queryCountData（只刷新角标，这是正确行为）
    │
    └─ AccountCondOrderPresenter.observeStockDeliverRefresh() 监听
         └─ if (moduleVisible) → emit(RefreshCurrentList) → loadData()
              ↑
              moduleVisible 始终为 false ← 这里断了
```

`moduleVisible` 为什么始终为 `false`？

追溯到 `AccountCondOrderViewModel.onModuleVisibleChanged()`：

```kotlin
// RecentCondOrderViewModel.kt:202
// 修改前：空实现，Fragment 调用了它，但什么都没发生
fun onModuleVisibleChanged(visible: Boolean) {}
```

Fragment 在 `initView()` 里调用了这个方法传入初始可见性，但方法是空的，没有把值同步给 Presenter，导致 Presenter 的 `moduleVisible` 从未被设置过，永远是默认值 `false`。

**修复：**

```kotlin
// 修改后：一行
fun onModuleVisibleChanged(visible: Boolean) {
    presenter.setModuleVisible(visible)
}
```

**编译验证：** `./gradlew :feature:trade:trade-order:compileDebugKotlin` → BUILD SUCCESSFUL

**评分 100/100，风险等级：低**

爆炸半径：直接调用方 1 处（`RecentCondOrderFragment.initView()`），单行改动，不影响任何数据流和接口逻辑，只修了初始化阶段的可见性同步。

**这个案例说明了什么：**

症状是"接口没被调用"，但根因是"一个空方法"。如果按症状修——在成交回报订阅里直接加列表刷新调用——代码能工作，但违反了职责边界：`SecondTabPresenter` 不应该知道条件单列表的刷新逻辑。

数据流追踪找到的是"本来应该工作的路径为什么没走到"，而不是"在哪里打一个补丁让它工作"。这是两种不同的调试思路，结果也不同。

**两个案例的对照：**

| | 案例 A（失败拦截） | 案例 B（成功修复） |
|---|---|---|
| Issue | #7067404642 | #7068108607 |
| 分析质量 | 深入但不确定 | 完整且确定 |
| 评分 | 70/100 | 100/100 |
| 阻塞原因 | 三条候选根因，需 logcat 判断 | 无阻塞 |
| 修复规模 | 未执行 | 1 行 |
| 流程输出 | 精准排查指引，等待日志 | 清单 + 提交就绪 |

案例 A 的"失败"不是流程失败，而是流程正确地识别了"现在动手是赌博"，并告知了最短路径。案例 B 的"成功"不是因为 bug 简单，而是因为分析方法找到了距离症状最远但距离根因最近的那个点。

## 总结

DevFlow 的 bug 修复流程本质上是在做一件事：**把工程师的隐性经验变成显性的流程约束**。

- 爆炸半径门禁，是把"有经验的工程师会先想清楚影响面"这条经验编码进流程；
- 90 分准入门禁，是把"分析不清楚不动手"这条原则变成可执行的规则；
- 人工验证门禁，是在保留工程师对代码的所有权；
- 强制复盘，是在把"每次修复都是一次学习"这条理念落地。

好的流程不是限制工程师的创造力，而是把工程师从重复性的判断疲劳中解放出来，让注意力集中在真正需要判断的地方。
