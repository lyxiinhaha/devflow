团队知识的两种死法

传统团队的工程经验，只有两个结局。

💬 死法一：口口相传

Review 时提一句「这里要注意 Token 刷新的并发问题」，下个月新同学来了，没人提，又踩了一次。

📄 死法二：文档归档

把踩坑记录写进 Confluence，三个月后没人看，六个月后没人找得到，一年后忘了有这个文档。

工程经验的核心矛盾：知识产生在个体，价值发挥在团队，但传递的管道太窄、太脆弱。
最终的代价是：相同根因的 Bug，换个人、换个模块，继续出现。

Karpathy 的视角

AI 写代码很快，但没有记忆

"Vibe coding is fun and great for prototypes. But it accumulates a form of technical debt that's harder to see — the AI doesn't know your system's history." — Andrej Karpathy，前 OpenAI / Tesla AI

Karpathy 指出的问题本质：每次新对话，AI 都从零开始。它不知道你们两个月前因为 Dialog 的 super.show() 让线上崩了一次，它不知道埋点必须通过模块级 object 收口，它不知道金额计算绝对不能用浮点数。

类比神经网络的训练数据

Karpathy 在 Software 2.0 里提到：神经网络的能力边界，由训练数据决定。

把这个类比搬到工程团队：AI 在你的项目上的能力边界，由你注入给它的上下文决定。
你的 Bug 经验卡，就是这个项目的「训练数据」。积累得越多，AI 在这个项目里越靠谱。

没有知识体系时

AI 凭通用知识写代码 → 不了解你们项目的历史 → 历史上踩过的坑，下次仍然会踩

有知识体系时

AI 接收项目专属经验 → 了解这个项目的雷区 → 写代码时自动规避已知问题

Layer 1

项目规则 project-rules.md

由同类经验卡蒸馏而来。每次 plan / code / review 自动置顶加载，始终生效，无需召回匹配。同一领域 N 张卡压缩为 1 条规则，token 开销固定可控。

## 埋点必须收口到模块级 object（来源：KB-030~KB-035，创建：2026-08-05）

所有埋点调用必须通过模块级 object 统一管理，禁止业务文件直接调用 SensorsTool。

禁止：
- Fragment/ViewModel 中直接调用 SensorsTool.sensorsOnEventAttach()
- Click 埋点放在网络请求回调或 dismiss 之后

必须：
- 每个模块新建独立 Sensor object 文件
- Click 事件在 setOnClickListener 内第一行触发
始终

案例一

CodeGraph 根因追踪 · 条件单成交回报不刷新

直觉修法：在成交回报订阅里直接加列表刷新。CodeGraph 追踪发现真正断点：

StockDeliverSubscription → AccountCondOrderPresenter.observeStockDeliverRefresh()
    → if (moduleVisible) → RefreshCurrentList → loadData()
           ↑
           moduleVisible 始终 false ← 根因在这里

// 真正的修复：一行代码
fun onModuleVisibleChanged(visible: Boolean) {
    presenter.setModuleVisible(visible)  // 原来是空方法
}

这次修复的根因已沉淀为经验卡，下次遇到类似「回调链中间某个 flag 没更新」的症状，会自动召回这个追踪模式。

完整闭环

让知识自我生长的五步循环

1

修完 Bug → 强制复盘写卡

devflow fix 四阶段根因分析完成后，强制触发 devflow retrospect。AI 提炼三个核心字段，不允许跳过：

root_cause
为什么出现，不是「是什么」
anti_patterns
下次绝对不能这样写
required_tests
这类问题必须加的测试
devflow fix KB-043 合规授权门禁被绕过
  root_cause:     fm == null 时直接降级执行受保护操作，跳过弹窗授权
  anti_patterns:  if (fm == null) { doProtectedAction() }  ← 永远不能这样写
  required_tests: fragment 为 null 时触发受保护操作的完整路径测试
  → 写入 KB-043，tags: compliance,auth,dialog
2

经验卡召回 → 直接变成任务约束

devflow plan 按当前需求的模块 / tag 召回相关卡，自动转化为 tasks.md 里的编码禁令和验收条目，工程师执行任务时直接看到约束，不需要提前知道历史。

## 任务 T-04：实现授权弹窗逻辑

- [ ] 弹窗继承 DTCommDialogFragment（禁止系统 AlertDialog）  ← KB-026
- [ ] show() 使用安全重载                                              ← KB-027
- [ ] FragmentManager 为 null 时禁止降级执行受保护操作                 ← KB-043

验收标准：
- [ ] Fragment 各生命周期阶段 show() 不崩溃
- [ ] fm == null 场景下受保护操作被正确拦截

每次召回都写入 knowledge-usage.jsonl：recalled_by / outcome / outcome_ts——记录这张卡在这个需求里有没有真正发挥作用。

3

同类卡积累 → 蒸馏为项目规则

同一 tag 下的卡达到阈值（默认 3 张），devflow knowledge distill tag=xxx 将多张卡的共性提炼为一条规则，写入 project-rules.md。

蒸馏前：6 张独立经验卡
KB-030 KB-031 KB-032
KB-033 KB-034 KB-035
各自按需召回，每次各占 token
蒸馏后：1 条项目规则
「埋点必须收口到模块级 object」
始终生效，6 张卡标记 distilled=true 不再召回

蒸馏前系统自动检查 project-rules.md 是否已有同 tag 规则，避免规则重复。参与蒸馏的卡标记 distilled=true 后退出召回池，只有 project-rules.md 里那一条规则继续生效。

4

规则失效检测 → 知识库自进化

写入新卡时，系统自动检测是否命中已有规则的 tag。若命中，提示规则可能需要加强——规则不是一次写完就永久有效，知识库也在进化。

⚠️ 规则「埋点必须收口到模块级 object」自建立后出现 2 次同类新卡
   KB-046（2026-08-15）  KB-047（2026-08-20）
   → 建议：修订规则覆盖新场景 / 个例单独保留 / 放弃规则

这个机制让规则不会变成「挂在墙上但已经过时的制度」，团队的实际行为会倒逼规则更新。

5

质量信号面板 → 定期清洁知识库

devflow knowledge check 分析 knowledge-usage.jsonl 中的召回记录，输出三类质量信号：

🏆 高价值卡
召回 ≥ 3 次
有效率 ≥ 60%
优先蒸馏为规则
👀 待观察卡
召回 ≥ 1 次
有效率 < 30%
复查描述是否准确
💤 沉睡卡
90 天内零召回
归档或删除

配合 devflow knowledge dedupe（去重）和 devflow knowledge prune（交互式清理）定期维护，知识库只保留真正有效的内容。

── 整体质量报告 ─────────────────────────────
  高价值卡  6 张   KB-027 KB-030 KB-033 KB-043 ...
  待观察卡  3 张   → 建议复查内容
  沉睡卡    2 张   → 建议归档
  整体有效率：74%（35 次召回中 26 次标记 applied）

── 蒸馏建议 ────────────────────────────────
  tag=dialog       5 张可蒸馏  → devflow knowledge distill tag=dialog

🔁 这是一个飞轮，不是一次性工作

每次 Bug 修复写一张卡，卡积累到阈值蒸馏为规则，规则在每次开发时自动保护团队，保护越好出 Bug 越少，出 Bug 反而带来新的高质量经验。
时间越长，这套系统对你们项目的理解越深，对新成员的保护越强。
知识库有效率随着 prune/distill 维护逐步上升，而不是随时间衰减。

团队协作

每个人都是知识库的贡献者

知识库存在项目的 git 仓库里（.devflow/config/templates/knowledge/），团队共用，提交共享。

每个人的日常

1
devflow fix 修复 Bug
2
devflow retrospect 写经验卡
3
git commit 推上去，团队共享

知识库维护者（每周）

1
devflow knowledge dedupe 去重
2
devflow knowledge distill 蒸馏
3
提交 project-rules.md，全员生效

工程师不需要主动「管理知识库」。
正常做 Bug 修复，正常写 retrospect，经验卡自然积累。
知识库的生长是研发流程的副产品，不是额外工作。

开始

三步，把知识闭环接入你的项目

第一步：安装

# Claude Code
claude plugins install devflow

# Cursor / Kiro / Codex / Gemini CLI
bash <(curl -fsSL https://raw.githubusercontent.com/lyxiinnaha/devflow/main/install.sh)

第二步：初始化项目

devflow init
# 自动检测技术栈、配置 CodeGraph、初始化知识库目录

第三步：从下一个 Bug 开始积累

devflow fix <bug 描述 或 Meegle 链接>
# 修复完成后，devflow retrospect 自动触发，经验卡自动入库

知识库从空开始，随着每次修复积累。
